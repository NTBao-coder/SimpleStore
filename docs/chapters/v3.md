# v3 — Tách Identity API và xác thực JWT

## Mục tiêu

Ở v2, Web/Admin vẫn đọc và ghi `identitydb` trực tiếp nên Identity chưa phải một service boundary.
v3 chuyển đăng nhập, đăng ký và quản lý người dùng sang Identity API; JWT cho phép service khác tự xác minh người gọi.

## Trước / Sau

```text
v2: Web/Admin → IdentityDbContext → identitydb
v3: Web/Admin → IIdentityApiClient → Identity.API → IdentityDbContext → identitydb
    Web/Admin → cache phiên phía server → JWT → Catalog.API (ghi cần role Admin)
```

## Những gì thay đổi

- `SimpleStore.Identity.API` sở hữu `IdentityDbContext`, model người dùng, migration và seed. `SimpleStore.Data`
  chỉ còn dữ liệu Order; Web/Admin không kết nối `identitydb`.
- Identity API cung cấp đăng ký, đăng nhập, refresh, logout, `/me` và quản lý user dành cho Admin.
  Access token sống 15 phút; refresh token sống 30 ngày, được lưu dưới dạng SHA-256 hash và xoay vòng khi refresh.
- `SimpleStore.Identity.API.Client` định nghĩa DTO và typed HTTP client. Web/Admin nhận cookie chỉ chứa mã phiên;
  access/refresh token nằm trong `IDistributedCache` phía server. Client tự refresh token gần hết hạn trước khi gọi API.
- Admin cần role `Admin`. Catalog vẫn cho phép đọc ẩn danh, còn CRUD yêu cầu JWT hợp lệ có role Admin;
  Catalog xác minh chữ ký, issuer, audience và hạn token tại chỗ.
- AppHost thêm resource `identity-api`, chỉ cấp `identitydb` cho service này và truyền cùng bộ cấu hình JWT cho
  Identity, Catalog, Web và Admin. `jwt-key` là Aspire secret parameter; issuer/audience demo là cấu hình thường.
- Migration `20261017164040_InitialIdentity` được chuyển nguyên ID sang Identity API để tiếp tục database v2;
  migration mới tạo bảng `RefreshTokens`.

## Quyết định thiết kế và đánh đổi (trade-off)

**Identity phát token, backend tự xác minh.** Mỗi request không cần gọi Identity để hỏi “ai là người dùng này”,
giảm một hop mạng và tránh đặt Identity trên đường đi của mọi thao tác. Đổi lại, mọi service phải giữ đúng issuer,
audience và signing key. Khóa HMAC là bí mật dùng chung nên cần được phân phối an toàn qua Aspire/user-secrets.

**Access token ngắn, refresh token dài và có thể thu hồi.** Token JWT ngắn giảm thời gian token bị dùng lại sau khi
bị lộ; refresh token cho phép phiên tiếp tục mà không yêu cầu người dùng đăng nhập lại. Chỉ lưu hash refresh token
giúp database không chứa giá trị bearer có thể dùng ngay. Xoay vòng làm luồng an toàn hơn nhưng tạo thêm trạng thái
và xử lý đồng thời; store khóa refresh theo phiên trong một tiến trình. Store hiện dùng `DistributedMemoryCache`,
nên phiên mất khi Web/Admin khởi động lại và chưa phù hợp chạy nhiều replica.

**Cookie BFF giữ token ngoài JavaScript.** Trình duyệt chỉ giữ cookie được bảo vệ chứa session ID; typed clients lấy
JWT từ cache phía server. Đây là cách tránh đưa bearer token vào local storage, nhưng vẫn thêm một kho phiên và
callback refresh vào mỗi ứng dụng frontend.

**Không chuyển passkey trong lát cắt này.** Bản trước có giao diện WebAuthn scaffold; các nút và trang passkey đã
được gỡ để tránh tiếp tục gọi `SignInManager` trong Web. Bảng passkey trong migration cũ vẫn được giữ, nhưng luồng
passkey chưa có endpoint Identity API. Đây là phần còn thiếu so với ghi chú upstream v3 và cần được thiết kế riêng.

**Migration giữ nguyên ID.** Database v2 đã ghi nhận migration Identity cũ; đổi ID sẽ khiến service mới cố tạo lại
các bảng `AspNet*`. Chuyển migration sang assembly mới và giữ ID cho phép service mới nhận quyền migrate mà không
đổi schema ban đầu. RefreshTokens được thêm bằng migration riêng.

## Cách kiểm tra

```bash
dotnet user-secrets set 'Parameters:jwt-key' "$(openssl rand -base64 32)" --project src/SimpleStore.AppHost
dotnet build SimpleStore.slnx -c Release
dotnet run --project src/SimpleStore.AppHost --launch-profile http
```

Trong Aspire, kiểm tra Identity API seed `demo@simplestore.local` / `Demo123!` và
`admin@simplestore.local` / `Admin123!`. Gọi `/api/identity/login`, dùng access token gọi `/api/identity/me`,
refresh bằng `refreshToken`, rồi thử dùng refresh token cũ lần nữa (401). Gọi Catalog CRUD không token để nhận 401,
với token Customer để nhận 403, và với token Admin để cho phép thao tác hợp lệ. Đăng xuất thu hồi refresh token.

Kết quả thực tế trong môi trường này: `dotnet build SimpleStore.slnx -c Release --no-restore -m:1
-p:UseSharedCompilation=false` thành công, 0 lỗi; còn 12 cảnh báo NU1902/NU1903 dependency MessagePack 2.5.192.
Docker không có trong PATH nên chưa chạy AppHost, migration trên PostgreSQL hay HTTP smoke checks.

## Câu hỏi tự kiểm tra

1. Vì sao Web/Admin không nên dùng `IdentityDbContext` dù vẫn ở cùng một solution?
2. Service kiểm tra claim nào để quyết định token do Identity tin cậy phát hành?
3. Vì sao database chỉ lưu hash refresh token nhưng client phải nhận giá trị raw?
4. Điều gì xảy ra khi Web/Admin restart với `DistributedMemoryCache`, và cần thay kho nào khi chạy nhiều replica?
5. Vì sao token role có thể không phản ánh thay đổi quyền ngay lập tức?
