# v2 — Tách Catalog thành dịch vụ HTTP

## Mục tiêu
Đưa quyền truy cập catalog về một dịch vụ duy nhất. Web và Admin dùng hợp đồng HTTP,
không còn biết entity, DbContext hay connection string của catalog.

## Trước / Sau

```text
v1: Web/Admin → CatalogDbContext → catalogdb
v2: Web/Admin → ICatalogApiClient → HTTP → Catalog.API → CatalogDbContext → catalogdb
```

Identity và Order vẫn nằm trong SimpleStore.Data, được Web/Admin truy cập trực tiếp.
Cart vẫn dùng session của Web; khi thêm sản phẩm mới vào giỏ, Web lấy thông tin qua Catalog API.
Chỉ Catalog được tách ở chương này.

## Những gì thay đổi
- Đánh thức hai project có sẵn: `SimpleStore.Catalog.API` và `.API.Client`.
- Chuyển model Product/Category, DbContext, factory, migration và catalog seed khỏi Data sang API.
  Giữ nguyên migration ID `20261017164026_InitialCatalog` và tên bảng để dùng tiếp catalogdb v1.
- Minimal APIs dưới `/api/catalog/products` và `/api/catalog/categories`: list, count, get by ID,
  POST, PUT và DELETE. Không thêm controller, JWT, gateway hay phiên bản `/api/v1`.
- Client chứa `ProductDto`, `CategoryDto`, `PagedResult<T>`, interface và lớp bọc HttpClient.
  DTO không chứa navigation EF. Client chuyển 404 khi lấy theo ID thành null; lỗi khác thành
  HttpRequestException, cho phép caller phân biệt “không có bản ghi” với “dịch vụ gặp lỗi”.
- Storefront dùng DTO, phân trang 12 sản phẩm. Admin dùng client cho CRUD, count và phân trang
  20 dòng. Danh sách chọn category duyệt các trang API để không bỏ sót category sau trang đầu.
- AppHost thêm resource `catalog-api`, cấp riêng catalogdb cho API. Web/Admin tham chiếu
  `catalog-api` và chờ dịch vụ này; hai frontend chỉ còn nhận orderdb và identitydb.
- Catalog tự migrate/seed; Web chỉ migrate Order/Identity và seed tài khoản.

## Quyết định thiết kế và đánh đổi (trade-off)
**Di chuyển quyền sở hữu cùng dữ liệu.** Nếu API mới vẫn để Web migrate catalog thì schema
còn phụ thuộc vòng đời frontend. Vì vậy migration và seed chuyển cùng context. Thay namespace
trong snapshot để khớp model mới nhưng giữ nguyên ID và cấu trúc schema: database v1 không
cần bị xóa. Nếu tạo lại migration initial với ID khác, EF có thể cố tạo các bảng đã tồn tại.

**DTO là hợp đồng của đường truyền.** ProductDto trả CategoryName thay cho entity Category.
Caller nhận đủ dữ liệu hiển thị, không thể tự viết Include/SaveChanges lên catalog.
Đổi lại có thêm mã ánh xạ và phải giữ API/client tương thích. Cả API và frontend tham chiếu
thư viện client trong bản học này; thư viện không tham chiếu Data hoặc EF.

**HTTP tạo thêm khả năng lỗi.** Trước kia câu gọi C# đi thẳng vào EF; giờ phải resolve địa chỉ,
serialize JSON và chờ phản hồi mạng. Base address `https+http://catalog-api` được service discovery
trong ServiceDefaults xử lý. AppHost truyền địa chỉ bằng WithReference, không hardcode cổng.
Khi chạy riêng, cấu hình `services:catalog-api:http:0` cho Web/Admin. Client giữ CancellationToken
và kiểm tra status code. Admin hiển thị lỗi HTTP khi CRUD thất bại; chưa có thiết kế chịu lỗi
hoàn chỉnh của các chương sau.

**Phân trang và thứ tự ổn định.** API trả Items, TotalCount, Page, PageSize; sắp theo Name rồi Id.
PageSize từ 1 đến 100, page phải dương. Cùng Name vẫn có thứ tự xác định nhờ Id. Các query có
lọc category/search được áp dụng trước Count/Skip/Take. Client bỏ categoryId khi null, thay vì
phát `categoryId=` khiến Minimal API không bind được số nguyên. Tìm kiếm được URL-encode.
Đây vẫn là offset pagination: dữ liệu thay đổi giữa hai request có thể làm dòng dịch chuyển.

**Bảo vệ quy tắc ngay tại API.** Product cần tên, giá/tồn không âm và category tồn tại; category
cần tên. Delete category còn sản phẩm trả 409, vì nút bị vô hiệu hóa ở Admin không thể bảo vệ
các caller khác. Các kiểm tra này phục vụ CRUD; chưa triển khai framework validation hay xử lý
mọi tình huống cạnh tranh đồng thời. API v2 chưa có xác thực, chỉ dành cho môi trường học nội bộ.

Thiết kế tham khảo: [ghi chú v2 upstream](https://github.com/daohainam/simple-store/blob/1b1ef8cbce79ba9ce16764c0501135e871e66b91/docs/v2-changes.md)
(MIT, Dao Hai Nam). Resource dùng tên `catalog-api` theo quy ước dự án.

## Cách kiểm tra

```bash
dotnet build SimpleStore.slnx -c Release
dotnet run --project src/SimpleStore.AppHost --launch-profile http
```

Bật Docker trước khi chạy AppHost. Trong dashboard, mở Catalog API, Web và Admin.
Catalog khởi tạo catalogdb; chờ Web khởi tạo Identity/Order trước khi vào Admin.

Các endpoint dùng chung cho `products` và `categories`:

```text
GET    /api/catalog/<resource>?page=1&pageSize=20
GET    /api/catalog/<resource>/count
GET    /api/catalog/<resource>/{id}
POST   /api/catalog/<resource>
PUT    /api/catalog/<resource>/{id}
DELETE /api/catalog/<resource>/{id}
```

Products còn nhận `categoryId` và `search`. POST thành công trả 201 cùng Location và DTO;
PUT/DELETE thành công trả 204. ID không tồn tại trả 404. JSON tạo sản phẩm ví dụ:

```json
{"name":"Learning item","description":"HTTP example","price":12.34,"stock":5,"categoryId":1,"imageUrl":""}
```

Thử tạo category, tạo product thuộc category đó, cập nhật product, đọc lại. Xóa category
khi vẫn có product phải trả 409; xóa product rồi xóa category phải thành công. Thử lọc,
phân trang, ID không tồn tại và pageSize sai. Trên Web, đăng nhập demo, thêm giỏ hàng,
đặt đơn rồi xem chi tiết. Trên Admin, mở dashboard, sản phẩm, danh mục, khách hàng và đơn hàng.

Kiểm tra migration từ project mới (EF CLI 10.0.7):

```bash
/tmp/simplestore-tools/dotnet-ef migrations has-pending-model-changes \
  --project src/SimpleStore.Catalog.API --context CatalogDbContext --configuration Release
# database update đọc ConnectionStrings__catalogdb từ môi trường.
/tmp/simplestore-tools/dotnet-ef database update \
  --project src/SimpleStore.Catalog.API --context CatalogDbContext --configuration Release
```

Kết quả thực tế:
- Build Release toàn solution: **0 lỗi**, còn 24 cảnh báo NU1902/NU1903 MessagePack 2.5.192
  từ dependency hiện có. Không thêm cảnh báo compiler.
- EF báo không có pending model changes; migration từ API áp thành công vào DB trắng.
- PostgreSQL 17 tạm chứa dữ liệu smoke v1: API khởi động, giữ đủ 10 sản phẩm, giữ tên sản phẩm
  đã sửa ở v1 và không chạy lại migration initial.
- Chương trình C# tạm dùng CatalogApiClient thật đã kiểm tra CRUD cả hai loại, count, phân trang
  không trùng dòng giữa trang 1/2, lọc category + tìm kiếm `A&B +`, 400/404/409 và null khi get 404.
- Web/Admin chạy **không có ConnectionStrings__catalogdb**; dùng service discovery trỏ API loopback.
  HTTP đăng nhập → giỏ hàng → checkout → confirmation/details/list thành công; cả năm trang Admin
  render 200 với dữ liệu đúng. Kiểm tra mã nguồn không còn CatalogDbContext/entity catalog ở frontend.
- **Chưa kiểm tra** AppHost/container vì không có Docker; chưa bấm CRUD qua kết nối Blazor
  tương tác trong trình duyệt. CRUD đã được kiểm tra qua cùng typed client mà Admin sử dụng.
